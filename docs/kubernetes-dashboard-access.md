# Kubernetes Dashboard Access With Vagrant and VMware

This note explains why the Kubernetes Dashboard may be installed correctly but still not open from the Windows browser.

## Problem

The Kubernetes Dashboard pods and services can be healthy:

```powershell
vagrant ssh controlplane -c "kubectl get pods -n kubernetes-dashboard"
vagrant ssh controlplane -c "kubectl get svc -n kubernetes-dashboard"
```

But this URL may not work directly from Windows:

```text
http://localhost:8001/api/v1/namespaces/kubernetes-dashboard/services/https:kubernetes-dashboard:/proxy/
```

## Root Cause

The Dashboard is exposed inside Kubernetes as a `ClusterIP` service.

`ClusterIP` services are reachable only from inside the Kubernetes cluster. They are not automatically exposed to the Windows host machine.

Most Dashboard examples use a `localhost:8001` URL because they expect `kubectl proxy` to be running on the same machine as the browser. In this setup, Kubernetes is running inside a Vagrant VMware VM, so there are two different `localhost` contexts:

- Windows `localhost` means the Windows host.
- VM `localhost` means the Vagrant control-plane VM.

Because the browser runs on Windows, it cannot directly access the Dashboard `ClusterIP` service.

## Working Access Flow

Use an SSH tunnel plus `kubectl proxy`:

```text
Windows browser
  -> localhost:8001
  -> Vagrant SSH tunnel
  -> controlplane VM localhost:8001
  -> kubectl proxy
  -> Kubernetes Dashboard ClusterIP service
```

## Start Dashboard Access

From this directory:

```powershell
cd C:\repository\spark-datalakeuhouse\vagrant-kubeadm-kubernetes
```

Run:

```powershell
vagrant ssh controlplane -c "kubectl proxy --address=127.0.0.1 --port=8001" -- -L 8001:127.0.0.1:8001
```

Keep this terminal open while using the Dashboard.

Then open:

```text
http://localhost:8001/api/v1/namespaces/kubernetes-dashboard/services/https:kubernetes-dashboard:/proxy/
```

## Login Token

The dashboard token is generated by the Vagrant provisioning script and saved here:

```text
C:\repository\spark-datalakeuhouse\vagrant-kubeadm-kubernetes\configs\token
```

Use that token on the Dashboard login page.

Do not commit this token to a public repository.

## Useful Checks

Check that the cluster is healthy:

```powershell
vagrant ssh controlplane -c "kubectl get nodes"
```

Check that Dashboard pods are running:

```powershell
vagrant ssh controlplane -c "kubectl get pods -n kubernetes-dashboard"
```

Check that the Dashboard service exists:

```powershell
vagrant ssh controlplane -c "kubectl get svc -n kubernetes-dashboard"
```

Check that the local proxy is reachable:

```powershell
Invoke-WebRequest -UseBasicParsing http://localhost:8001/api/
```

Expected result: HTTP status `200`.

## Interview Explanation

Use this short explanation:

> The Dashboard was running correctly, but it was exposed as a Kubernetes `ClusterIP` service, which is internal to the cluster. Since my browser runs on the Windows host and Kubernetes runs inside a Vagrant VMware VM, I used `kubectl proxy` inside the control-plane VM and an SSH tunnel from Windows to the VM. This allowed me to access the Dashboard securely through `localhost:8001`.

## Production Note

For a real production cluster, the Kubernetes Dashboard is often avoided or tightly restricted. If enabled, access should be protected with proper authentication, RBAC, network restrictions, and audit controls.
